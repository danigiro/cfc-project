# Simulation experiment

This README provides step-by-step instructions for reproducing the simulation
experiments detailed in the paper.

Run all commands with `cfc_sim` as the working directory.

## Instructions for reproducing the experiment

 1. `./run_bal.sh`: balanced framework\
    `./run_unb.sh`: unbalanced framework

    Each script loops over 54 configurations (6 settings x 3 numbers of experts
    `p` in {4, 10, 20} x 3 sample sizes `N` in {50, 100, 200}), for both the
    `cor` and `diag` estimators of the covariance matrix, and writes one `.rds`
    file per configuration in `results/<framework>_hier_<cor|diag>/`.

 2. `Rscript R/extract_score.R`: collect the scores of every configuration into
    four summary files in `score/`.

 3. `Rscript R/tables.R [cor|diag]`: produce the LaTeX tables in `tables/`, for
    the `cor` (*default*) or the `diag` estimator of the covariance matrix. Run
    it twice, once per estimator, to obtain all the tables of the paper:

    ```bash
    Rscript R/tables.R cor
    Rscript R/tables.R diag
    ```

## Intermediate files

Re-running step 1 is not necessary to reproduce the results of the paper. Two
sets of intermediate files are available on request from the authors:

| Directory  | Produced by                  | Content                                            | Size   |
|------------|------------------------------|----------------------------------------------------|--------|
| `results/` | step 1 (`sim_*_parallel.R`)  | raw output, one `.rds` per configuration (216 files)| ~21 GB |
| `score/`   | step 2 (`extract_score.R`)   | MSE and MAE of every configuration, four `.rds`     | ~390 MB|

`results/` is too large to be distributed with this package, and `score/` is
shipped only on request for the same reason. Depending on which files you have,
you can enter the pipeline at any point:

-   with `results/`: start from step 2;
-   with `score/`: start from step 3, which reproduces every table of the paper
    in a few seconds.

## Runtime

**The simulations are very time consuming: about 165 hours (roughly 7 days) of
computing time in total**, on the machine described below and with 15 parallel
workers. Measured wall-clock time of the original run:

| Framework  | Covariance | Configurations | Total    | Per configuration (median) |
|------------|------------|----------------|----------|----------------------------|
| balanced   | `cor`      | 54             | 79.8 h   | 82 min                     |
| balanced   | `diag`     | 54             | 39.3 h   | 41 min                     |
| unbalanced | `cor`      | 54             | 20.4 h   | 22 min                     |
| unbalanced | `diag`     | 54             | 25.2 h   | 23 min                     |
| **Total**  |            | **216**        | **165 h**|                            |

Runtime grows quickly with the number of experts `p` and the sample size `N`, so
the per-configuration figures above are medians over a wide range: individual
configurations differ substantially from the average.

Steps 2 and 3 are cheap: `extract_score.R` takes a few minutes, `tables.R` a few
seconds. **The tables of the paper can be reproduced with step 3 alone**, without
re-running the simulations, using the intermediate files described above.

## Parallel computing

Both simulation scripts use `foreach` over a `future` backend:

```r
registerDoFuture()
plan(multisession, workers = 15)
```

The number of workers is set at the top of `R/sim_bal_parallel.R` and
`R/sim_unb_parallel.R` (line 9) and must be adjusted to the number of cores and
to the amount of memory available: each worker holds its own copy of the data.
Reducing the number of workers increases the runtime proportionally but **does
not change the results**: the random number
streams are fixed with `doRNG::registerDoRNG(367429)`, which assigns each
iteration its own reproducible stream independently of how the iterations are
distributed across workers.
